## Технические вызовы

### 1. Парсинг AsyncAPI 3.0 спецификаций
**Проблема:** Сложная структура вложенных ссылок между channels, operations и components  
**Решение:** Создание рекурсивной функции extractMessage для обработки различных типов ссылок

### 2. Сопоставление каналов
**Проблема:** Необходимость найти совместимый канал поставщика по протоколу и структуре сообщений  
**Решение:** Алгоритм сравнения required полей в payload сообщений

### 3. Экранирование имен каналов
**Проблема:** Слэши в именах каналов экранируются как ~1 в JSON Pointer  
**Решение:** Функции escapeChannelName и unescapeChannelName

## Разработка Parser модуля для AsyncAPI 3.0

**Дата разработки:** 18 июля 2025  
**Время разработки:** ~45 минут  
**Цель:** Создание минималистичного парсера для преобразования AsyncAPI спецификаций из строки в типизированные структуры

### Предпосылки

После создания модуля валидации каналов возникла необходимость в универсальном парсере, который бы:
- Преобразовывал строковое представление спецификаций в типизированные структуры
- Поддерживал все необходимые элементы для валидации контрактов (headers, payload, bindings)
- Был легковесным и расширяемым

### Анализ альтернатив

Рассматривались два варианта:
1. **Использование asyncapi/parser-go** - официальной библиотеки
2. **Создание минималистичного решения**

Выбрали второй вариант, так как:
- Полный контроль над функционалом
- Минимальные зависимости
- Точное соответствие нашим потребностям
- Легкая интеграция с существующим кодом

### Реализованный функционал

#### 1. Структуры данных (types.go)
Созданы полные типизированные структуры для всех элементов AsyncAPI 3.0:
- **AsyncAPISpec** - корневая структура спецификации
- **Channel, Operation, Message** - основные компоненты
- **Schema** - универсальная структура для headers и payload
- **Bindings, CorrelationId** - дополнительные метаданные
- **Components** - переиспользуемые компоненты

#### 2. Основной парсер (parser.go)
- **ParseFromString/ParseFromBytes** - парсинг из различных источников
- **Валидация версии** - поддержка только AsyncAPI 3.x
- **Работа со ссылками** - резолвинг $ref
- **Обработка экранирования** - корректная работа с именами каналов

#### 3. Вспомогательные функции (helpers.go)
- **ExtractChannelProtocol** - извлечение протокола через серверы
- **ExtractOperationMessages** - получение всех сообщений операции
- **CompareMessageSchemas** - сравнение совместимости схем
- **ValidateAsyncAPIVersion** - проверка версии спецификации

### Особенности реализации

1. **Поддержка headers и payload**
   - Полная структура Schema для описания данных
   - Сравнение по required полям
   - Поддержка вложенных объектов

2. **Работа с bindings**
   - Сохранение protocol-specific настроек
   - Поддержка bindings на уровне каналов и сообщений

3. **CorrelationId**
   - Парсинг location и description
   - Поддержка для request-reply паттернов

### Тестирование

Создан полный набор тестов:
- Парсинг валидных спецификаций
- Обработка невалидного YAML
- Тестирование helper функций
- Проверка совместимости схем

**Результаты:** Все тесты проходят успешно, время выполнения ~4ms

### Интеграция

Parser модуль готов к интеграции с:
- Существующим channel validator
- Будущим contract validator (по ROP паттерну)
- CLI интерфейсом

### Итоги

Создан минималистичный, но функциональный parser для AsyncAPI 3.0 спецификаций, который:
- Полностью покрывает потребности валидации контрактов
- Имеет типизированные структуры для всех элементов
- Легко расширяется при необходимости
- Хорошо протестирован

Модуль parser завершен и готов к использованию в системе валидации контрактных тестов.

## Реорганизация архитектуры проекта

**Дата разработки:** 18 июля 2025  
**Время разработки:** ~2 часа  
**Цель:** Решение проблемы циклических зависимостей и создание единой архитектуры

### Предыстория

После создания parser и contract_validator модулей возникла проблема циклической зависимости:
- `channel` импортировал `contract` (для использования ContractValidate)
- `contract` импортировал `channel` (для вызова channel validator)
- `parser` был в отдельном пакете

Go компилятор не позволяет циклические зависимости, что блокировало компиляцию проекта.

### Решение

Принято решение объединить все модули в один пакет `validator` с разделением по файлам:

**До реорганизации:**
```
contract-tests-v2/
├── channel/
│   ├── validator.go
│   └── validator_test.go
├── contract/
│   ├── validator.go
│   ├── types.go
│   └── validator_test.go
└── parser/
    ├── parser.go
    ├── types.go
    ├── helpers.go
    └── parser_test.go
```

**После реорганизации:**
```
contract-tests-v2/
└── validator/
    ├── types.go                 # Все типы и структуры
    ├── parser.go               # Парсер AsyncAPI 3.0
    ├── contract_validator.go   # Contract validator (ROP паттерн)
    ├── channels_validator.go   # Channel validator (адаптированный)
    └── validator_test.go       # Объединенные тесты
```

#### 1. Создание единого файла типов (15 минут)

## Устранение дублирования типов и финализация валидации каналов

**Дата разработки:** 19 июля 2025  
**Время разработки:** ~3 часа  
**Цель:** Рефакторинг архитектуры, устранение дублирования кода и завершение реализации валидации каналов

### Контекст проблемы

После объединения модулей в пакет `validator` была обнаружена критическая проблема: типы AsyncAPI были продублированы между пакетами `parser/` и `validator/`. Это приводило к:

- **Дублированию ~100+ строк кода** с идентичными определениями типов
- **Потенциальной рассинхронизации** при изменении структур в одном пакете
- **Нарушению принципа DRY** (Don't Repeat Yourself)
- **Сложности в поддержке** двух версий одних и тех же типов

### Анализ масштаба проблемы

**Дублированные типы:**
```go
// В validator/types.go (ДУБЛИРОВАННЫЕ)
type AsyncAPISpec struct { ... }
type Channel struct { ... }
type Message struct { ... }
type Server struct { ... }
type Operation struct { ... }
type Components struct { ... }
type Schema struct { ... }
// ... еще ~10 типов

// В parser/types.go (ОРИГИНАЛЬНЫЕ)
type AsyncAPISpec struct { ... }
// ... те же типы
```

### Поэтапное решение

#### Этап 1: Планирование и анализ (30 минут)

**Задачи в TODO:**
1. [high] Проанализировать дублирование типов между parser и validator
2. [high] Удалить AsyncAPI типы из validator/types.go  
3. [high] Обновить все импорты в validator для использования parser.AsyncAPISpec
4. [high] Запустить тесты после устранения дублирования

**Принятое решение:** Сделать пакет `parser/` единственным источником истины для AsyncAPI типов

#### Этап 2: Устранение дублирования типов (45 минут)

**Действия:**
1. **Удалили дублированные типы** из `validator/types.go` (строки 41-144)
2. **Добавили импорт** `parser` пакета во все файлы validator
3. **Заменили все ссылки на типы:**
   - `AsyncAPISpec` → `parser.AsyncAPISpec`
   - `Channel` → `parser.Channel`
   - `Message` → `parser.Message`
   - `Server` → `parser.Server`
   - `Operation` → `parser.Operation`
   - И т.д. для всех типов

**Затронутые файлы:**
- `validator/types.go` - удалены дублированные типы
- `validator/channels_validator.go` - обновлены все методы
- `validator/contract_validator.go` - исправлены сигнатуры функций
- `validator/parser.go` - обновлены все типы
- `validator/validator_test.go` - исправлены mock данные

#### Этап 3: Архитектурная очистка (40 минут)

**Проблемы legacy кода:**
- Папка `channel/` содержала устаревший код (600+ строк)
- Функция `validateChannels` в contract_validator была лишней оберткой
- Смешанные ответственности между модулями

**Решения:**
1. **Удалили папку `channel/`** полностью:
   - `channel/validator.go` - legacy реализация
   - `channel/validator_test.go` - устаревшие тесты

2. **Упростили contract_validator:**
   ```go
   // БЫЛО (избыточная обертка)
   validationResult, err := v.validateChannels(contractValidate)
   
   // СТАЛО (прямой вызов)
   _, err = v.channelValidator.ValidateChannels(contractValidate)
   ```

3. **Убрали лишнюю функцию `validateChannels`** - она просто перенаправляла вызов

#### Этап 4: Реализация полной логики валидации каналов (60 минут)

**Требования из Шага 3 ТЗ:**
> Необходимо по структурам спецификациям собрать новую выходную структуру, которая содержит:
> - канал потребителя (имя, протокол, исходящее/входящее сообщение)
> - канал поставщика (имя, протокол, входящее/ответное сообщение)

**Реализованные алгоритмы:**

1. **Извлечение информации о канале потребителя:**
   ```go
   func (v *ChannelValidator) extractConsumerChannel(contractValidate *ContractValidate) (*ChannelInfo, error) {
       // 1. Получаем канал из спецификации
       // 2. Извлекаем протокол через servers
       // 3. Находим operations с action="send"  
       // 4. Извлекаем outMessage и inMessage (reply)
   }
   ```

2. **Поиск соответствующего канала поставщика:**
   ```go
   func (v *ChannelValidator) findMatchingProviderChannel(...) (*ChannelInfo, error) {
       // 1. Перебираем все каналы поставщика
       // 2. Фильтруем по протоколу
       // 3. Извлекаем сообщения из operations с action="receive"
       // 4. Проверяем совместимость структур сообщений
       // 5. Возвращаем первый совместимый канал
   }
   ```

3. **Валидация совместимости сообщений:**
   ```go
   func (v *ChannelValidator) areMessagesCompatible(msg1, msg2 *MessageInfo) bool {
       // Сравниваем по required полям
       required1 := v.getRequiredFields(msg1.Payload)
       required2 := v.getRequiredFields(msg2.Payload)
       
       // Все required поля должны присутствовать в обеих схемах
       for _, field := range required1 {
           if _, exists := props2[field]; !exists {
               return false
           }
       }
       return true
   }
   ```

4. **Обработка $ref ссылок:**
   - Ссылки на компоненты: `#/components/messages/UserSignup`
   - Ссылки в каналах: `#/channels/user~1signedup/messages/signup`
   - Рекурсивное разыменование вложенных ссылок

5. **Экранирование имен каналов:**
   ```go
   // user/signedup → user~1signedup (JSON Pointer escaping)
   func escapeChannelName(name string) string {
       return strings.ReplaceAll(name, "/", "~1")
   }
   ```

#### Этап 5: Исправление проблем с тестами (35 минут)

**Проблема:** Тесты падали с ошибкой "no compatible provider channel found"

**Root cause анализ:**
- Mock спецификации в тестах не содержали секции `operations`
- Отсутствовали `components` с описанием сообщений
- Без этих данных валидация не могла найти совместимые каналы

**Решение:**
```go
// Добавили полные operations для потребителя
Operations: map[string]parser.Operation{
    "sendUserSignup": {
        Action: "send",
        Channel: parser.ChannelRef{Ref: "#/channels/user~1signedup"},
        Messages: []parser.MessageRef{{Ref: "#/components/messages/UserSignup"}},
    },
}

// Добавили компоненты с полными схемами
Components: &parser.Components{
    Messages: map[string]parser.Message{
        "UserSignup": {
            Name:        "UserSignup",
            ContentType: "application/json",
            Payload: &parser.Schema{
                Type: "object",
                Properties: map[string]parser.Schema{
                    "userId": {Type: "string"},
                    "email":  {Type: "string"},
                },
                Required: []string{"userId", "email"},
            },
        },
    },
}
```

**Дата разработки:** 20 июля 2025  
**Время разработки:** ~2 часа  
**Цель:** Исправление алгоритма выбора каналов и добавление comprehensive тестов

### Предыстория

После завершения основной реализации валидации каналов пользователь запросил добавить тест для случая, когда у поставщика есть несколько каналов с одинаковым протоколом, но разной структурой сообщений. Алгоритм должен выбирать канал по совместимости сообщений, а не просто по протоколу.

### Обнаружение критического бага

#### Шаг 1: Написание теста (15 минут)

Создали тест `TestChannelValidator_MultipleProviderChannels` со следующим сценарием:
- **Потребитель:** канал `user/events` с сообщением UserSignup (userId, email, name)
- **Поставщик:** 3 канала с протоколом AMQP:
  1. `notifications/users` - UserSignup (совместимый)
  2. `notifications/orders` - OrderEvent (несовместимый)
  3. `notifications/products` - ProductEvent (несовместимый)

**Ожидание:** Алгоритм выберет `notifications/users` как единственный совместимый канал.

#### Шаг 2: Обнаружение проблемы (10 минут)

Тест упал с неожиданным результатом:
```
Expected: notifications/users
Actual: notifications/orders
```

**Root cause:** Функция `findMatchingProviderChannel` возвращала первый канал с подходящим протоколом, не проверяя структуру сообщений.

### Исправление алгоритма

#### Шаг 3: Анализ кода (20 минут)

Проблемный код:
```go
func (v *ChannelValidator) findMatchingProviderChannel(...) (*ChannelInfo, error) {
    for channelName, channel := range providerSpec.Channels {
        if protocol == consumerProtocol {
            // БАГ: Возвращаем первый канал без проверки сообщений
            return &ChannelInfo{...}, nil
        }
    }
}
```

#### Шаг 4: Исправление с проверкой совместимости (25 минут)

**Решение:** Добавить проверку совместимости сообщений перед возвратом:
```go
if consumerChannel.OutMessage != nil && inMessage != nil {
    if !v.areMessagesCompatible(consumerChannel.OutMessage, inMessage) {
        continue // Структуры не совпадают, ищем дальше
    }
} else {
    continue
}
// Нашли совместимый канал
return &ChannelInfo{...}, nil
```

### Обнаружение второго бага

#### Шаг 5: Тестирование исправления (15 минут)

После исправления тест все еще падал. Отладка показала, что функция `getRequiredFields` возвращала пустой массив для всех сообщений.

**Root cause:** `convertSchema` возвращал `[]string` для required полей, а `getRequiredFields` проверял только тип `[]interface{}`.

```go
func areMessagesCompatible(msg1, msg2 *MessageInfo) bool {
    // 1. Проверяем ContentType
    if msg1.ContentType != msg2.ContentType {
        return false
    }
    
    // 2. Извлекаем required поля
    required1 := getRequiredFields(msg1.Payload)
    required2 := getRequiredFields(msg2.Payload)
    
    // 3. Проверяем что все required поля есть в обеих схемах
    for _, field := range required1 {
        prop1 := props1[field]
        prop2 := props2[field]
        
        // 4. Проверяем типы полей
        if getFieldType(prop1) != getFieldType(prop2) {
            return false
        }
    }
    
    return true
}
```
