# Анализ подходов к тестированию в контексте бережливой разработки, TBD и Continuous Deployment
Я поддерживаю бережливый и прогрессивный подход к разработке и тестированию с непрерывной поставкой в прод.
В гит работа идет по trunk based development.
Используются фича тоглы, контрактные тесты Pact Broker.

Можно код компонентных тестов на геркин хранить в репозитории проекта и в отдельном проекте - это позволит упростить интеграцию тестов в CI.
При таком подходе какой подход к написанию тестов микросервисов предпочтительнее, 
а какой более компромисный?

Важно учесть, что код тестов - это документация.

## Понимание подхода

Мною описан прогрессивный подход к разработке, использующий:
- Бережливую (Lean) разработку
- Trunk Based Development (TBD)
- Continuous Deployment
- Feature Toggles
- Контрактное тестирование с Pact Broker
- компонентные тесты

Эта комбинация направлена на максимальную скорость доставки качественного кода с минимальными накладными расходами и рисками.

## Оптимальное решение для эффективной разработки с компонентными тестами

### Предпочтительный подход:
**Хранение компонентных тестов на Gherkin в том же репозитории, но в отдельном модуле/проекте**

Это подход имеет следующие преимущества, идеально соответствующие моей стратегии:

1. **Синхронизация с фичами и контрактами**: 
   - При изменении API изменения кода, тестов и контрактов Pact происходят атомарно
   - Снижается риск рассинхронизации при быстрых изменениях в Trunk Based Development

2. **Поддержка быстрых циклов CD**:
   - CI сразу получает обновленные тесты вместе с кодом
   - Нет задержки между выпуском фичи и обновлением тестов
   - Быстрее подтверждение того, что feature toggle работает правильно

3. **Упрощение TBD**:
   - Разработчики видят и понимают тесты вместе с изменениями кода
   - Тесты на Gherkin в том же репозитории служат "живой" документацией
   - Упрощается ревью кода, когда тесты и код изменяются вместе

4. **Структурная гибкость**:
   - Отдельный модуль/проект внутри репозитория обеспечивает логическое разделение
   - Возможность иметь отдельные конфигурации сборки для тестов
   - Тесты можно легко запускать изолированно

## Более компромиссный подход:

**Хранение компонентных тестов в отдельном репозитории с автоматической синхронизацией**

Этот подход можно рассматривать как компромисс, если:
- У нас несколько команд, работающих над разными аспектами системы
- Тестовая инфраструктура сложна и требует специального управления

Для минимизации недостатков этого подхода нужно обеспечить:
1. **Автоматические уведомления о несоответствиях**: Интеграция с Pact Broker, чтобы сразу выявлять нарушения контрактов
2. **Автоматические пул-реквесты**: Настройка системы, которая предлагает изменения тестов при изменении API
3. **Блокирование деплоя**: Настройка CI/CD, чтобы блокировать деплой, если тесты не обновлены

## Почему первый подход предпочтительнее

В контексте TBD и Continuous Deployment критически важна **скорость и надежность изменений**. Первый подход лучше соответствует этим требованиям по следующим причинам:

1. **Принцип единой ответственности**: Команда, меняющая код, также отвечает за тесты
2. **Снижение когнитивной нагрузки**: Разработчикам не нужно думать о синхронизации между репозиториями
3. **Feature toggles + тесты**: Легче контролировать, что выключенная функция не влияет на существующие функции
4. **Меньше коммуникационных накладных расходов**: Не требуется координация между командами, поддерживающими разные репозитории

## Практические рекомендации по реализации

Для оптимальной реализации первого подхода рекомендую:

1. **Структура репозитория**:
   ```
   /my-service
     /src              <- Код сервиса
     /component-tests  <- Отдельный модуль с компонентными тестами
       /src/test
         /resources
           /features   <- Gherkin спецификации
         /java         <- Реализация шагов
     /contract-tests   <- Тесты для Pact Broker
   ```

2. **Интеграция с CI/CD**:
   - Настроить отдельный этап для компонентных тестов
   - Кэширование Docker-образов для ускорения тестов

3. **Связь с Feature Toggles**:
   - В компонентных тестах явно указывать, какие feature toggles должны быть включены/выключены
   - Обеспечить тестирование как с включенными, так и с выключенными toggles

4. **Документация**:
   - Автоматически генерируйте документацию из async api спецификаций
   - Интегрируйте результаты нагрузочных компонентных тестов в систему мониторинга

## Заключение

В контексте нашего подхода (бережливая разработка + TBD + CD + feature toggles + Pact) однозначно предпочтительнее хранить компонентные тесты в том же репозитории. 
Это обеспечивает оптимальный баланс между скоростью разработки, контролем качества и поддерживаемостью.

Такой подход соответствует принципам бережливой разработки, минимизируя потери на координацию и синхронизацию, 
а также принципам TBD, обеспечивая быстрое и надежное продвижение изменений через пайплайн.
